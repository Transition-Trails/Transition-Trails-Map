I have four related pieces of work on the learner routes and the prompt template routes. I have verified the Salesforce schema facts below against production directly, so please treat them as given rather than re-deriving them.

First, the assignments query. GET /api/learner/assignments queries Course_Module_Activity__c filtering on Learner__c and Due_Date__c. Neither field exists on that object — it is the curriculum catalogue, describing activities per module rather than per person. Production also carries two objects that are not in our data model workbook: Course_Enrollment__c and Course_Activity_Completion__c. Please describe both, work out which one carries a learner's own progress against activities, and rebuild the assignments query on it. If neither gives us a due date, tell me rather than substituting something approximate — a learner's assignment list without dates is still useful, an invented date is not.

Second, quest submission. POST /api/learner/quest/submit writes Learner__c to Penny_Quest_Submission__c. That field does not exist. The object's real fields are Assignment__c (a required lookup to Course_Module_Activity__c), Submission_Text__c, Submitted_At__c, and Name. So the insert fails twice — a field that is not there, and a required field that is not supplied. Please correct the mapping and write the learner's answer into Submission_Text__c; it currently goes to Gemini for feedback and is then discarded.

The required Assignment__c link raises a design question I would like your read on. It means the schema expects a quest to be tied to a real curriculum activity, and Course_Module_Activity__c carries a Quest_Eligible__c flag whose help text says only activities where it is true may be used as source material for quest generation. Our daily quest route ignores that and asks Gemini to invent a quest from the learner's trail and phase. Please tell me what it would take to generate quests from eligible activities instead, and what we lose by doing so. Do not change the generation behaviour yet — I want to decide that separately.

Third, and regardless of the above: a failed Salesforce write must not return success. sfCreate and sfPatch return null or false rather than throwing, so the route continues and returns { success: true } with points and feedback even when nothing was recorded. Please make a failed submission return an error the interface can show. The same applies to sfQuery, which returns an empty array on failure — a failed query and a genuinely empty result should be distinguishable by the caller.

Fourth, the prompt template routes. POST and PATCH /api/penny/prompt-templates carry no authorisation; only the seed route has requireAdmin. Approving a template is what makes it reach a learner, so please require admin on both, and enforce the self-approval rule where the record is saved rather than in the panel that renders the button. Right now reviewRequestedBy is checked in the UI, so the control does not survive a direct call to the endpoint.

Two smaller things while you are in these files. The learner routes use API version 59.0 while the rest of the server is on 62.0 — please align them. And they authenticate with a static SF_SERVICE_TOKEN rather than the connector path the other routes use; tell me whether that is deliberate before changing it, since it may be the only way these routes work without a user session.

Please run a typecheck and the full suite when done, and add tests covering the corrected field mappings. Then tell me which of the schema questions above you could not answer from the org.
