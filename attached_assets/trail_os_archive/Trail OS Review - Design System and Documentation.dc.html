Platform review

Trail OS against the design system and its own documentation

Twenty-six findings across three areas. The design-system gap is the same one the public site had in July — no tokens, hand-approximated color, non-brand type — but it runs deeper here because Trail OS uses six extra hues to carry meaning. Two findings matter more than any of the visual work, and neither is a styling problem: RESOLVE is defined differently in Trail OS than in the Master Program Guide, and the coach ladder does not exist in the access model.

What the color actually is

Trail OS defines its palette as HSL triplets in index.css, hand-tuned rather than converted from the brand hexes. Converted back to hex, the drift is visible: the green is mintier, the teal is duller and darker, and the body text is a cool blue-grey where the brand is a warm grey-green.

Design system

12 findings

Trail OS imports no design-system tokens. Everything below follows from that one fact.

TOS-DS-01

Blocker

No design-system tokens are imported

The app defines its own palette from scratch as HSL triplets in a local :root block. Nothing links to the TTDS token files, so every brand decision has been re-derived by hand and can drift again.

Recommendation — the same move that fixed the public site: add tokens.css as the single source of truth and redefine the existing shadcn variables as aliases pointing at it. No component edits, no visual regression risk beyond the intended color correction.

TOS-DS-02

Blocker

None of the brand typefaces are loaded

Trail OS runs on Inter and Playfair Display. Inter is on the brand book's explicit avoid list; Playfair appears nowhere in TTDS. Poppins, Open Sans and Caveat are absent, and so is the Fraunces display ruling taken for the public site in July.

Recommendation — Open Sans for body and UI, Poppins for H3–H4, buttons and labels, Fraunces for H1–H2 to match the site. Caveat has no role in an internal operations tool; leave it out rather than find a use for it.

TOS-DS-03

Blocker

Primary and secondary are approximations of the brand colors

See the comparison above. Neither the green nor the teal matches, and side by side with the public site the two products do not look like the same organization.

Recommendation — resolved by TOS-DS-01. Once the variables alias the tokens, this corrects itself.

TOS-DS-04

Blocker

The app reads cool where the brand is warm

Body and heading text resolve to a blue-grey. TTDS specifies Slate for body and Charcoal for headings — both warm, both with green in them. This single value does more to make Trail OS feel like a different product than any other finding here.

Recommendation — resolved by TOS-DS-01. Worth looking at first after the token swap, because it changes everything at once.

TOS-DS-05

Ruling

Cards are beige on a beige page

The card surface and the page background differ by about two percent in lightness, so the border carries the entire visual hierarchy. TTDS puts white cards on Trail Light, which is what gives the brand its airy feel.

Recommendation — white cards, Sky tint for nested or secondary surfaces. This is a bigger perceptual change than it sounds, which is why it is a ruling rather than a fix.

TOS-DS-06

Blocker

Six non-brand hues carry meaning

Emerald, sky, violet, indigo, rose, amber and slate appear in over fifteen hundred class strings in the page files alone — as status colors, as program colors, as card accents. TTDS has four colors and caps a surface at one or two backgrounds. This is the largest single visual gap, and unlike the others it cannot be fixed by a token swap.

Recommendation — collapse to four semantic roles: success on Trail Green, information on Deep Teal, attention on Amber 700, neutral on Warm Grey. Where a category genuinely needs distinguishing, use one shape or icon difference rather than a new hue.

TOS-DS-07

Blocker

The amber rule is broken systemically

Amber is doing four jobs in Trail OS: a warning status, a program color, the executive lens color, and sidebar chrome. The brand book allows one amber call to action per screen and forbids decorative use. Several admin screens carry a dozen amber elements and no amber button.

Recommendation — the same ruling taken on the site in July: amber earns one primary action per screen. Status and warning move to Amber 700 as text on a light tint, never as fill, and never on the same screen as an amber button.

TOS-DS-08

Ruling

Corners are about half the brand radius

Buttons render at six pixels and cards at twelve. TTDS specifies fourteen for buttons and inputs and twenty-two for cards, described as "soft and approachable". At current values Trail OS reads sharper and more technical than the brand intends.

Recommendation — raise to the brand scale. In a dense operations tool this is a real aesthetic choice, not a compliance one, so it needs your eye on one screen before it goes everywhere.

TOS-DS-09

Ruling

Focus rings are one pixel

Buttons and inputs use a one-pixel ring in the theme color. TTDS specifies a three-pixel Trail Green ring at low opacity, which is also the better accessibility answer for keyboard users on a data-dense tool.

Recommendation — adopt the brand ring. Same correction already applied to the public site.

TOS-DS-10

Cleanup

Shadows and hover behavior are framework defaults

Cards use the default shadow rather than the brand's soft low-contrast one, and nothing lifts on hover. TTDS asks for a three-pixel lift over about a sixth of a second — the gentle motion that carries the "calm confidence" the brand describes.

Recommendation — token-level fix, applies everywhere at once.

TOS-DS-11

Ruling

Dark mode has no brand basis

Trail OS ships a complete dark palette. TTDS v2.0 has no dark specification at all, so whatever dark mode looks like today is invention, and it is the version staff will use at night.

Recommendation — either author dark tokens into TTDS v2.1 properly, or remove the theme until you want to. Leaving an unspecified dark mode in a tool you are documenting for funders is the option to avoid.

TOS-DS-12

Blocker

Type runs far below the brand's minimum sizes

Interface text sits at eight, nine, ten and eleven pixels throughout — sidebar labels, badges, table cells, panel captions. The brand floor for labels and small text is fourteen. This is the app's largest accessibility exposure and the one a funder or a partner is most likely to raise.

Recommendation — raise the floor to fourteen and let the layout absorb it. This is real work, not a find-and-replace: several dense tables and the collapsed sidebar were designed around the smaller sizes.

Documentation

8 findings

Trail OS is better documented than most projects at this stage — a full specification, contribution guide, security policy, changelog and roadmap. The problem is not absence. It is that three documents describe three different products, and the gaps that remain are the ones a new coach or a funder would hit first.

TOS-DOC-01

Blocker

The README and the working notes disagree about what is live

The README lists Gemini and Agentforce as Phase 2 and Google OAuth as in progress. The working notes and the roadmap list Penny on Gemini, Agentforce, Gmail, Calendar, Drive and Google Auth as live. The README is the first thing anyone reads, and it currently understates the platform by six integrations.

Recommendation — one integration table, generated from or manually mirrored to the readiness file the code already treats as authoritative. Everything else links to it.

TOS-DOC-02

Blocker

The documented navigation is not the navigation in the app

The working notes describe seven sidebar groups named Navigator, Operations Center, Demand Management, Penny Command Center, Knowledge Library, Collaboration and Administration. The sidebar actually renders Digital Twin, Operations, Programs, Penny, Knowledge, Collaboration and Administration. The README's table is the accurate one.

Recommendation — the sidebar definition is already a single array. Document the structure once from that file and delete the second table.

TOS-DOC-03

Ruling

The access tiers are stated more than one way

The README describes four tiers including Super Admin. The sidebar and the access configuration gate on Everyday, Power and Admin. Whether Super Admin is a real tier or a label on the Admin tier needs confirming before it appears in a permissions matrix a funder reads.

Recommendation — state the tier model once, in one file, and have the docs quote it.

TOS-DOC-04

Blocker

The coach ladder does not exist in Trail OS

Coach's Assistant, Associate Coach and Advanced Coach are central to the Master Program Guide and to how the verdict rework curve is meant to calibrate. Trail OS has no concept of them — access is Everyday, Power and Admin, resolved from Google Groups. This was already on your list as the coach calibration protocol; Trail OS is where it has to land.

Recommendation — coach level is a separate axis from access tier. An Associate Coach and an Advanced Coach may both be Power users, but their verdicts have to be distinguishable. Model it as its own field before the dashboard is built against the specification.

TOS-DOC-05

Ruling

There is no data dictionary

Thirty-three files and well over a megabyte of prototype data sit in the data folder, and nothing says which of it is real, which is illustrative, and which will be replaced by a live query. The working notes give this one line. Anyone demonstrating Trail OS is one click from a number they cannot defend.

Recommendation — one table: file, what it holds, prototype or live, and what replaces it in Phase 2. This is also the fastest way to find out how much of the app is still illustrative.

TOS-DOC-06

Ruling

There is no design documentation

No token reference, no component usage guidance, no accessibility statement. There is an in-app UX standards page, which is the right instinct, but it is not reachable by anyone who has not logged in and it is not what a contractor or a new developer reads.

Recommendation — a short design document in the repo that states the token source, the four semantic status roles, the amber rule, the type floor and the radius scale. Five hundred words prevents the next fifteen hundred hardcoded colors.

TOS-DOC-07

Cleanup

The app still ships placeholder metadata

The page title is "Program Map Dashboard" and the description reads "built on Replit. Update this description to reflect the app." That is the browser tab, the bookmark and the link preview any staff member sees.

Recommendation — Trail OS, Transition Trails, plus a one-line internal description. Two minutes.

TOS-DOC-08

Ruling

No glossary reconciled to the Master Program Guide

The terminology file governs platform labels — Trail Signals, Trail Insights, Penny, Mission Control — and does it well. But the words the programs run on appear nowhere: verdict, rework curve, squad, buddy pair, Base Camp, Decision Log. Penny coaches learners using this vocabulary.

Recommendation — one glossary, owned by the Master Program Guide, referenced by Trail OS rather than restated in it.

Content and methodology

6 findings

These matter more than the visual findings. Trail OS teaches RESOLVE through Penny, and right now it teaches a different RESOLVE.

TOS-CON-01

Blocker

RESOLVE is a different methodology inside Trail OS

Trail OS defines eight phases. The Master Program Guide defines seven. Only Recognize, Verify and Evolve appear in both.

Trail OS today

Recognize · Evaluate · Solve · Organize · Leverage · Verify · Execute · Evolve

Master Program Guide

Recognize · Explore · Select · Outline · Launch · Verify · Evolve

Recommendation — the Guide and the RESOLVE Handbook are the authority; Trail OS should be rewritten to the seven phases. Worth checking whether the eight-phase version predates the Handbook, because the two named phases that only exist in Trail OS suggest it was reconstructed from the acronym rather than from the source.

TOS-CON-02

Blocker

"Source mapping needed" is visible in the product

Six of the eight phases carry that placeholder in their inputs, outputs, owner and implications fields, and the Execute phase is flagged as needing review with a note openly questioning whether it is a real phase. Those fields render in the app.

Recommendation — fill them from the RESOLVE Handbook as part of the seven-phase rewrite. The confidence flag itself is a good pattern and worth keeping.

TOS-CON-03

Ruling

Program roster needs reconciling

The home screen colors four programs. The Master Program Guide now carries eight, including Trail of Mastery's four tracks, First Two Weeks and the three Explorer's tiers. Whether the program data behind Trail OS has kept up needs checking before anything is demonstrated from it.

Recommendation — reconcile the program data against the Guide, same exercise as the public site in July.

TOS-CON-04

Ruling

"Trailhead" appears seventeen times

Most are legitimate references to Salesforce's actual platform — resource links, module maps — and those are fine. Two sit closer to the line the brand book draws: a standards field named "Trailhead Link", and coaching copy that offers learners "Trailhead mix-ins". The prohibition is on the term as Transition Trails vocabulary, not on naming an external platform.

Recommendation — rename the field to "External Resource Link" and keep external references as plain references. Your call on how tightly to hold the line.

TOS-CON-05

Ruling

"Trail Quests" is quest language

There is a Trail Quests surface in the Penny section and a Quest Master capability. The brand book rules out the Salesforce ecosystem's gamified vocabulary and asks for milestone and stage language instead. Quest sits in the same register as the terms it names.

Recommendation — either confirm Trail Quests as deliberate house vocabulary and write it into the brand book, or rename. It is already centralised in the terminology file, so renaming is cheap now and expensive after learners see it.

TOS-CON-06

Cleanup

Emoji are carrying status

The README and roadmap use tick, hourglass and clipboard marks as their status system, and one screen renders a lightning bolt in front of a Penny mapping. The brand book is explicit that emoji are not part of the brand and that status is carried by an icon paired with text.

Recommendation — plain status words in the documents, the existing icon set in the interface.

Suggested order

Each step is safe to stop after, and none of them requires the next one to have happened.

1

Take the five rulings

Fonts, dark mode, categorical color, the type floor, and who owns RESOLVE. Nothing else is safe to start until these are settled.

2

Land the token layer

Tokens as the source of truth, existing variables redefined as aliases, brand fonts, brand radius, brand focus ring, brand shadows. One file, no component edits. This closes seven findings at once and is the same change that worked on the public site.

3

Fix RESOLVE

Seven phases, filled from the Handbook, placeholders gone. Content work, entirely independent of the styling, and the finding with the most at stake because Penny teaches from it.

4

Collapse the six hues to four roles

One shared status map, then a sweep through the pages. Big and mechanical. This is the equivalent of the hex collapse still outstanding on the public site, and it should not start before the ruling in step one.

5

Documentation set

One README as truth, one integration table, a data dictionary, a design document, and the glossary pointed at the Master Program Guide. Then the type floor, which is the only remaining item that needs layout judgment rather than a decision.

Five decisions

Everything else follows from these.

Does an internal tool get the full brand type?

Fraunces for H1 and H2 matches the public site but is unusual in an operations product. The alternative is Poppins for all headings and Fraunces reserved for outward-facing surfaces.

Keep dark mode or drop it?

Keeping it means authoring dark tokens into the brand book. Dropping it is one line and removes an unspecified surface.

Do programs need their own colors?

Trail OS currently gives each program a hue. Four brand colors cannot carry eight programs, so either the brand book gains a categorical ramp or programs are distinguished by label alone.

How far do you want to go on the type floor?

Fourteen pixels everywhere is the brand answer and the accessible one, and it will make several dense screens taller. A staged version raises the worst cases first.

Confirm the Guide owns RESOLVE.

If the seven phases in the Master Program Guide are authoritative, Trail OS gets rewritten. If the eight-phase version encodes something real, the Guide needs to change instead — and that affects Penny, the Decision Log and every program document.
