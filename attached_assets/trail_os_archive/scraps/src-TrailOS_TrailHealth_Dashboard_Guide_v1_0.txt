About this document: This guide explains what the TrailHealth Dashboard is, where every number comes from, and how the health of each dimension is defined. It is the reference document for Angela, Kim, Hugh, and Michele — so that any team member can understand what they are looking at, verify the source of any data point, and update the dashboard correctly when the org or the programs change.
## 1. What the TrailHealth Dashboard Is
The TrailHealth Dashboard is Transition Trails' weekly operating pulse — a single HTML file that surfaces live data from the Salesforce org and Google Analytics into a structured five-tab view for Angela, Kim, Hugh, and Michele. It replaces the need to open Salesforce reports, check Zapier logs, or manually compile a status update before the team's weekly touchpoint.
The dashboard serves two purposes simultaneously. It is an operational health monitor — a real-time view of the org, the programs, and the digital presence as they exist today. And it is a build governance tool — it tracks which Trail OS capabilities have been designed and which have been deployed, surfacing the gap between architecture and production so the team never loses track of where the system actually is.
Core principle: the dashboard surfaces what is true, not what is planned. Every metric is sourced from a live system or a dated document. Where data is estimated or sourced from a document rather than a live pull, the source is labelled explicitly.

## 1.2 How to Use the Dashboard
Open the HTML file in any browser — it requires no server or login. Click Refresh data to trigger a manual pull. The Salesforce MCP connection runs live queries against the production org each time the dashboard is opened or refreshed. GA4 data updates on Mondays via Zapier.
Each tab is independent. Navigate by clicking the tab bar. Flags and attention items appear inline within each tab — there is no separate notifications pane. The footer of each tab shows the data source and the last updated timestamp for that section.

## 3. How Health Is Defined
The term 'health' in the TrailHealth Dashboard is deliberate and specific. It does not mean everything is working. It means the team has clear visibility into what is working, what is not, and what the next action is. A system where every flag is green is healthy. A system where every flag is red but all flags are surfaced, and owners are assigned, is also healthy. A system where problems exist but are not visible is not healthy.
Health definition: an org, program, or capability is healthy when its current state is accurately known, the gap between current state and target state is explicitly documented, and every gap has an owner and a next action. Visibility is health. Surprise is the failure mode.

## 3.3 Program Health — How Cohort Progress Is Measured
The Program Health tab calculates each cohort's progress toward its end date as a simple linear percentage: (days elapsed since start date) ÷ (total duration in days) × 100. This is displayed as a coloured progress bar alongside the cohort name and date range.
This is a time-based measure, not a completion-based measure. It shows how far through the scheduled window a cohort is — not whether learners are on track within that window. Learner-level completion tracking requires the Assessment and Program Engagement stage data to be cleaned (E-02) before it can be computed accurately.

## 3.5 Penny & Agentforce — How Readiness Is Measured
The Penny & Agentforce tab does not use a percentage score. Readiness is assessed against the five-phase build sequence defined in the Agentforce & Data Cloud Capability Guide v1.0. Each phase has a gate — a specific condition that must be met before the next phase can begin. The dashboard shows which phase each component is in and whether its gate is met.
The primary readiness blocker at the time of this document is not technical — it is data quality. The Agent Builder cannot produce reliable results until the data foundation (Phase 1) is complete: Program Engagement records are cleaned, 10+ Knowledge articles are published, Employee records are seeded, and Contact learner fields are built. License headroom is not a constraint — 10,000 Agent Builder PSLs and 200,000 Data Cloud seats are provisioned.

## 4.1 What Gets Flagged vs. What Does Not
Not every data point that is below target appears as a flag. Flags are reserved for items that require a decision or action this week. Known roadmap gaps that are sequenced and documented (e.g., 'LMS not yet built — Epic E-10 target Q1 2027') appear in the capability status sections, not as flags.
A flag appears when: (1) a live data pull reveals something different from what was expected, (2) a governance rule is being violated in the current state, (3) a P0 or P1 issue is open and unresolved, or (4) a time-sensitive opportunity exists — for example, a batch of learners who applied 11 months ago when a new cohort is 8 weeks from opening.

## 5.2 When to Regenerate the Dashboard
The dashboard HTML file is static between refreshes — it does not auto-update. Regeneration (producing a new version of the HTML file) is needed when:
New capability tab needed — a new Trail OS capability has been documented and built and deserves its own tab.
Scorecard dimensions change — new health dimensions are identified or existing ones are retired.
Major build milestone — a capability moves from In Design to In Production and all its in-design flags become in-production confirmations.
Data source changes — a new MCP connection is added, a Zapier zap is rebuilt, or GitHub is connected for live test counts.
Minor updates — correcting a flag, adjusting a score, adding a note — can be made by editing the HTML directly.
