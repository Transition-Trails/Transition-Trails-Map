F-05-05 · design

Making Prompt Studio change what Penny says

Prompt Studio is in better shape than the backlog suggested. Ten templates already exist with a full governance lifecycle, and the studio already has a working test runner that calls the real Penny endpoint with a real learner selected.

What is missing is not a screen. It is that the templates live in a source file, nothing reads them at request time, and — the part that needs deciding before any code is written — the templates were written to replace Penny's identity rather than to sit inside it.

CORRECTION · 4 AUGUST

Templates are already database-backed. This document said they were not.

Prompt templates have persisted in the platform database since mid-July, with create, update and seed routes, a live editing panel and an auto-seed on first load. The claim below that they live in a source file is wrong.

Two consequences. Sub-feature 05-05c is already complete. And moving templates to Salesforce — agreed on my recommendation — is a migration away from something working, not a first build, so it is worth re-deciding rather than inheriting.

Everything else in this design stands, including the central finding: the templates still assert their own identity, and nothing yet feeds them to the layer assembler. See the change review of 4 August for the full picture.

What is already built

Worth establishing first, because it changes the size of the job considerably.

Ten real templates, not placeholders

Learning coach, resume review, LinkedIn review, weekly reflection, knowledge answer, coach brief, executive brief, study plan, post-module reflection, and a coach-only alert. Each carries a full prompt body, an intent, variables and an output shape. These are authored, considered artefacts.

The governance lifecycle already exists

Every template has a status: draft, in review, approved, or deprecated. Nothing enforces it yet, but the model is right and the governance policy already says a Penny capability below quality threshold gets suspended. The scaffolding for safe editing is designed.

A live test runner is already wired

Prompt Studio can pick a real learner from the directory, call the real endpoint, and report which context layers contributed and how long it took. The feedback loop this feature needs is built — it just is not running the template being edited.

And the pattern to copy already works

Trail configurations are Salesforce records, edited through a Trail OS screen, and read by the layer assembler at request time. That is precisely what templates need. This feature is mostly doing for templates what already works for trails.

Decide this before writing code

Every template opens by telling Penny who she is

Nine of the ten begin with a variation of "You are Penny, a supportive Salesforce learning coach for Transition Trails." They were written as complete, standalone prompts — because when they were authored, there was no layer assembler to sit inside.

There is now. Layer one already establishes who Penny is for this audience. If a template body is dropped in as layer four unchanged, every request carries two identity statements — and where they differ, the model resolves the conflict however it likes. Today the built identity is an internal operations assistant, while most templates assert a learner coach. That is not a subtle tension; it is two different jobs in one prompt.

The resolution: layer one owns identity, layer four owns the task. Each template gets its identity preamble removed and keeps what is genuinely task-specific — the situation, the steps, the output shape, the constraints. That is an authoring pass over ten templates and it should happen before they are loaded anywhere, not after.

What a template should contain

Once identity moves out, the boundary becomes clear — and it is a useful editorial rule for whoever writes the next one.

Belongs in the template

Belongs in another layer

What this particular task is, and when it applies

The steps to work through, in order

The shape of the output — sections, length, whether it ends in a question

Task-specific constraints, such as never sending a coach-only alert to a learner

Which context this task needs, so a missing input is a clear failure rather than a vague answer

Who Penny is, and her tone — layer one

The trail's own configuration and focal points — layer two

The learner's phase, focus and blockers — layer three

Retrieved knowledge and its sources — the knowledge layer

Anything about a specific person, which changes per request and cannot be authored

One consequence worth naming. Templates currently interpolate variables such as a learner's name directly. Those must resolve from the context the layers already assembled, not from a second lookup — otherwise two parts of the same prompt can disagree about who is being talked to.

Where templates should live

The question underneath this: is editing a prompt a content change or a code change? A Penny Admin is a governing role, not a developer, so it has to be possible without a deployment. That rules out leaving them in source.

Recommendation: a Salesforce custom object, following the trail configuration pattern exactly. Records rather than metadata, so they are authored directly and do not need promoting through environments. Permission-controlled by the same permission set that will govern the integration user. Audit trail and approval come from the platform rather than being rebuilt.

Why not the local database

It would work and it would be quicker. But the local database currently holds telemetry only, and that boundary is already one of the more confusing things about the platform. Putting behavior-governing content there makes it a second system of record, and the next person has to learn which of two stores holds what. The cost is small today and compounds.

One caution from experience this week: the new object needs a status field, and if it is a restricted picklist the four lifecycle values must be created before anything writes to it. That is exactly the class of failure that stopped Penny's interaction log ever recording a single row.

How a template gets chosen

The endpoint currently takes no notion of which task is being performed, so this needs adding. Three ways in, and the design should be explicit about which is which rather than guessing.

Named by the caller — the normal case

A scheduled Slack brief, a resume review, a study plan: the caller knows what it is asking for. The Slack integration already carries a template reference on each of its message types, which means wiring this unlocks Slack message generation at the same time rather than as separate work.

A default per audience — the open conversation

Someone simply asking Penny a question has not named a task. A learner should get the knowledge-answer template, an admin the operations behavior. One default per audience, configured rather than hardcoded.

Inferred from the question — deliberately not yet

Classifying intent to pick a template is appealing and adds a layer of unpredictability to a system nobody can currently observe. Worth revisiting once template performance is measurable, and not before.

Editing safely, and knowing it worked

The moment this ships, a text box in an admin screen changes what Penny says to a learner. Two safeguards make that acceptable rather than alarming.

Only approved templates reach a real request. The lifecycle already exists in the data; this gives it force. A draft is visible only to the test runner, so an admin can edit and try repeatedly without touching anyone. Approval is the deliberate act that makes an edit live.

Every response names the template and version that produced it. The layer report already exists and already says which layers contributed — it should say which template too. Without that, a changed answer and a changed prompt cannot be connected, and the studio becomes a place where people make changes hopefully.

The test that proves this feature is done

Edit a template, save it as a draft, run the same question against the same learner twice — once before the edit, once after — and see two different answers with the version difference named in the report. Anything less and the studio is still describing rather than driving.

Decisions — settled 4 August

Templates live in Salesforce. Confirmed. The trail configuration pattern is the model, so the object is records rather than metadata, authored directly, and read by the assembler at request time.

Approval requires Penny Admin. Confirmed, and it should be enforced on the write rather than only hidden in the interface — moving a template to approved is the act that changes what a learner hears, so it belongs behind the same kind of check that guards secrets and group administration. Everyone else may edit a draft; only a Penny Admin can make it live.

The coach-only alert stays out of the wiring. It is not live and needs further work. Seed it as a record so the content is not lost, leave it in draft, and give the object an audience field from the start — so when it is finished, the constraint that it must never reach a learner is enforced by routing rather than by a sentence inside the prompt.

That leaves nine templates in scope for the wiring, and one waiting on its own design.
