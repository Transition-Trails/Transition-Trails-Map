What Penny actually is today

Audited from the code, not the documents. Penny in Trail OS is a real Gemini integration with real retrieval — better than the roadmap claims in two places. But the pieces are not joined to each other, nothing is persisted, and the seventeen Penny screens in the interface have almost no influence on what she actually says.

There is also one defect I would fix today, before anything else on this list.

DEFECT

The conversation history filter lets bad data through

The history validator in the Ask Penny route checks that each item has a valid role and that its text is a string. Because && binds tighter than ||, the condition actually reads "role is user, or role is model and text is a string" — so for any item whose role is user, the text check never runs.

A malformed user turn — missing text, or text that is a number or an object — passes validation and gets sent to Gemini as an undefined part. That surfaces as an unexplained failure from Penny rather than a clear error, and it will be intermittent, which makes it expensive to diagnose later.

Fix — parenthesise the role comparison so the text check applies to both roles. One line. Worth doing before the feature work, because multi-turn history is about to be used much harder.

Better than documented

Two things the roadmap lists as future work are already built. Worth knowing before anyone scopes them again.

Multi-turn conversation works

The route accepts a history array, caps it at the last ten turns to control tokens, and maps it into the Gemini request properly. The roadmap lists conversational memory as planned future work. The transport is done.

The gap is persistence, not capability — history is supplied by the browser, so it dies with the tab.

Retrieval is real, and better than expected

A genuine relevance scorer over the knowledge corpus: stop-word removal, weighted matching across name, category, snippet and full text, a boost for confirmed sources, tier filtering, normalized scores, and source links returned.

This is not a stub. It is a working keyword retrieval engine and it only needs joining up.

What is not connected

the real state of Penny

Every piece exists. None of them know about each other.

Retrieval and generation are joined by the browser

The Ask Penny route accepts already-retrieved chunks in its request body. It never calls retrieval itself. So the client has to make two calls in the right order, and any screen that forgets the first one silently gets an ungrounded answer with no indication anything is missing. Source attribution depends on the caller too.

Nothing Penny says is stored

No database write, no Salesforce record, no log of what was asked or answered. Every conversation is lost on refresh, there is no way to review a learner's history, and there is no data to measure her against — which means none of the engagement metrics in the six-pager can currently be computed.

The prompt has three parts, not seven

What is assembled today: a static identity block, a role paragraph, and retrieved sources. What the architecture calls for and is absent: trail configuration, learner context, active quest, career review state, and the capability prompt template.

The consequence worth naming: Prompt Studio is one of the largest screens in the application and nothing authored there reaches a real response. Same for the capability registry. Those screens describe an architecture the server does not implement yet.

Tier is whatever the client says it is — even though the server knows better

Clerk middleware is mounted across the whole API, so a verified identity is attached to every request that reaches Penny. Both routes ignore it. They read the user's tier and role from the request body instead, and neither requires a session — Clerk's middleware attaches auth state, it does not enforce it.

So tier filtering on the knowledge corpus is advisory: anything that can reach the endpoint can claim any tier and receive the full corpus. The good news is that this is a much smaller fix than it sounds — the identity is already there and already trustworthy. It just is not being read.

Penny has one identity where she needs several

Penny serves internal Trail OS users, learners, coaches, and eventually clients — with the Product Vision adding a public-facing guide for prospects and donors. Five audiences, and they want genuinely different things from her.

What is built is one identity: the system prompt defines her as "AI Chief of Staff", with domains covering integrations, secrets audits and readiness dashboards. That is the internal Penny, and it matches Vision E-05 precisely — so it is right, not wrong. The other four are represented only by a short role paragraph appended underneath it.

A paragraph cannot override an identity. Asking the chief-of-staff prompt to be "clear and encouraging" for a learner produces an operations assistant using warmer words — not a Socratic coach who asks before telling. The difference between the two is behavioral, and behavior comes from the identity layer, not from a tone instruction.

Durable rate limiting and a cost ceiling

Move the limiter off in-memory per-IP state, and add a daily token or spend ceiling with an alert. Acceptance: limits survive a restart, apply per user rather than per address, and a runaway loop cannot quietly spend the month's budget.

F-02-01

E-02

One identity layer per audience, selected at request time

Penny serves five audiences and has one identity. Replace the single static prompt with a selectable identity layer: internal staff keeps the chief-of-staff framing that exists today; the learner identity is the Socratic coach who asks before telling; the coach identity drafts for approval rather than answering directly; the client identity is bounded to case status and knowledge routing with a human approval gate; and the public identity handles program fit and donation pathways without ever coaching.

Acceptance: the same question from a learner and from an admin produces recognizably different behavior, not just different vocabulary — a learner gets a question back, an admin gets an answer. Identity is chosen from the resolved session, never from a request parameter. Maps to Vision epics E-01 through E-08; build internal and learner first, coach and client when those surfaces exist.

Critical

F-02-02

E-02

Give Penny real learner context

Populate the trail and learner layers from Salesforce — trail, phase, week, current focus, recent win, current blocker — instead of leaving them absent. Acceptance: asking "what should I work on this week" returns an answer naming the learner's actual position, and the same question from two learners returns two different answers.

Critical

The order I would take them

Fix the defect first — it is one line and it makes everything after it easier to debug. Then the layer assembler, because five of the remaining features are additions to it and building them separately means building it five times.

Then persistence, then server-side retrieval. Those two together are what turn Penny from a demonstration into something measurable — and until exchanges are stored, none of the engagement targets in the six-pager can be reported to a funder.

The two learner features wait on one decision from you: whether the learner surface is Experience Cloud, Trail OS, or Slack. The work is the same in all three cases, but where it renders is not.
