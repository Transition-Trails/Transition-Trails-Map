Trail OS — Contributor Pack

Everything you need to work on Trail OS without breaking it. Written for a developer or contractor joining the build, not for someone using the product.

Current as of 4 August 2026. Where this document and the code disagree, the code is right — please correct the document.

1 · What Trail OS is

Transition Trails trains Salesforce professionals through real client work paired with structured skill development. Trail OS is the internal staff platform that runs it — a control room over Salesforce, Slack, Google Workspace and Gemini, with an AI assistant called Penny woven through it.

Two things it is not. It is not the system of record — Salesforce is, and Trail OS reads from it. And it is not yet a learner-facing product; coach and learner views are planned inside Trail OS but not built.

The single most useful thing to understand early: the product evolved while the approach was being worked out. Documents that predate a decision still describe the old one. GitHub is current state; if a document disagrees with the code, the document is stale.

2 · How the code is arranged

Four workspaces. Two matter for most work:

api-server — the Express API. Every integration lives here: Salesforce, Slack, Gemini, Google Workspace, and authentication. Around 115 route handlers across 28 files.

program-map — the React front end. Pages are grouped by navigation section; the sidebar definition is a single array and is the authoritative description of the app's structure. If you want to know what Trail OS contains, read that file rather than any document.

mockup-sandbox and scripts — supporting. The sandbox carries two pre-existing type errors that are not yours to fix and do not affect anything.

Six navigation groups

Operations · Programs · Penny · Knowledge · Collaboration · Administration. Digital Twin is an item inside Administration, not a group of its own — several older documents get this wrong.

3 · Where the data comes from

This is the section to read most carefully, because a screen showing a number tells you nothing about where that number came from. There are three sources, and roughly two thirds of the data files are still illustrative.

Source What it holds
Salesforce, live The system of record. Contacts, programs, cases, curriculum, Penny's trail configurations. Read through the Replit connector proxy.
Local database Telemetry only — Penny's model, latency and resolved tier per exchange. Not a second system of record, and not a cache of Salesforce.
Illustrative fixtures Around twenty files of invented data written to make screens demonstrable. Every figure in them is made up. They carry a marker; respect it.

If you are replacing a fixture with a live query, the honest test is whether a change made in Salesforce appears in Trail OS without a code change. Anything short of that is still a fixture wearing a live query's clothes.

The Salesforce model, in brief

Eighteen custom objects in three families — eight for Penny, six for curriculum and progress, four for build governance. Seventeen are deployed and readable. Four hold data today: course, module and activity records, plus the four Penny trail configurations. The rest are empty, which is expected.

Two reuse decisions matter more than anything else here. There is no learner object — a learner is a Contact, with program membership expressed through Program Engagement and around twenty-eight organization-specific custom fields on Contact itself. And curriculum reuses the course objects rather than creating parallel ones.

This is where stale documents will mislead you most. Older specifications name objects like a standalone learner object or separate conversation objects. Those were superseded by the data model and never created. Always check the org before creating anything.

4 · Identity and access

One identity, three grants. Understanding this distinction will save you a day.

Google is the identity provider. Sign-in is Google OAuth restricted to the organization's domain — and it validates the domain claim in the returned token, not just the request hint. There is no other login. A separate administrator wizard also exists for granting the application service access to Drive, Calendar and Gmail; it looks like a login flow and is not one. Do not confuse them.

Google Groups determine access. At sign-in, the person's group memberships are resolved through the Directory API and held on the session as a set. Never collapse that set to a single level when making a decision — somebody can hold both Penny governance and platform governance, and those are different domains rather than rungs on a ladder. A display tier is derived from the set for the interface; it is a label, not the authority.

Salesforce and Slack are separate grants. A Google token proves who someone is; it does not authorize Trail OS to read Salesforce or post to Slack. Each issues its own tokens. Because Salesforce signs in through Google as its SAML provider, that grant costs the user one consent click and no password.

Authorization is default-deny. Keep it that way.

A single gate runs before every router mount: every route requires staff authentication unless it is explicitly listed as public, and that list is deliberately tiny — the two OAuth round-trips, the wizard callbacks, a signature-verified webhook, and a health check. Secrets, group administration and role owners carry a second administrator check.

If you add a route, it is protected automatically. Adding something to the public list is a decision, not a convenience — and it should be justified in the pull request.

5 · How Penny works

Penny runs on Gemini. She serves five audiences — internal staff, learners, coaches, clients and eventually the public — though only the internal identity is built today. The others are currently a tone instruction on top of it, which changes vocabulary rather than behavior.

Her system prompt is assembled from seven independent layers, each a separate function. Every layer is optional and contributes nothing when it has no data — an empty layer is normal, not a failure. The response reports which layers actually contributed, which is how you debug prompt quality.

Layer State
Identity — who Penny is for this audienceInternal only
Trail context — the program configurationLive from Salesforce
Learner context — phase, focus, blockersLive from Contact
Knowledge — retrieved sourcesWorking
Active questEmpty — object has no records
Career reviewEmpty — object has no records
Memory window — recent exchangesDepends on persistence

Two things about the architecture that are easy to get wrong. Retrieval is currently orchestrated by the browser — the endpoint accepts already-retrieved sources from the caller, so a screen that forgets to fetch them gets an ungrounded answer that looks identical to a grounded one. Moving that server-side is open work. And the prompt studio does not yet drive real responses; templates authored there have no effect until that is wired.

The write of each exchange to Salesforce is deliberately fire-and-forget: a failed write must never cost the user their answer. That is correct, and it has a cost you need to know about — see the lessons below.

6 · Conventions to follow

Design

The design system is the source of truth and it is implemented as a token layer. Do not introduce a color, a typeface, a radius or a shadow that is not in it. Specifically:

Four brand colors and five semantic status roles. There is no red in the palette; the attention color is amber, used as text on a light tint rather than as a fill. One amber call to action per screen, never decorative — amber on a badge that appears on every screen breaks this without looking like it does.

Poppins for headings, Open Sans for body and interface. Fourteen pixels is the floor for any text, including table cells, badges and sidebar labels. This was raised from as low as eight and is easy to reintroduce.

Status is never carried by color alone — pair it with an icon and text. No emoji, in the product or in repository documents.

Language

RESOLVE has seven phases: Recognize, Explore, Select, Outline, Launch, Verify, Evolve. It is the delivery methodology every program teaches, and an earlier eight-phase version in the code was wrong and has been corrected. If you find eight anywhere, it is stale.

Work is judged by verdict, not by grade: pass, needs rework, or not attempted. Never a percentage. The measure of a learner is their rework curve over time.

The brand avoids the Salesforce ecosystem's own vocabulary — a few such terms survive in field names and are being relabeled rather than migrated. "Trail Quests" is deliberate house vocabulary and is not one of them.

7 · Lessons paid for already

Five failures found in this codebase, each of which cost real time. They are not hypothetical and they will recur if you do not know them.

A failure and a zero must never look the same

Operations queries once swallowed every error and returned nothing, so a permissions problem and a genuinely empty result were indistinguishable. A dashboard reporting no active programs when the real answer is a misspelled picklist value is worse than an error, because it looks like information.

A throttled response is not an absence

The connector proxy rate-limits at twenty requests per ten seconds. Probing eighteen objects in parallel exceeded it, and the page reported nine of them as inaccessible when they were fine. Worse, a throttled field describe returned nothing and was reported as fields being missing — which would have sent someone to create fields that already existed. Anything you cannot determine needs a third state, and it must not read as absent.

Validate written values against the real schema

Penny's interaction log never wrote a single record. The code sent a source value that was not among the picklist's permitted options, so Salesforce rejected every insert. It went unnoticed for as long as it did because the tests mock the Salesforce client — they assert that a write is attempted with certain values, never that those values are legal. Mocked tests prove intent, not conformance.

Fire-and-forget needs somewhere to shout

Swallowing a write failure so the user keeps their answer is the right design. But it made a total, permanent failure look exactly like success from every angle anyone checked. If you write something asynchronously, make its last failure visible somewhere a person will actually look.

One caught exception can disable far more than you think

A throw on a missing contact was caught two lines later and nulled the Salesforce client for the entire request — so staff users silently had no trail configuration, no learner context and no history, not merely no log entry. When something is missing for one purpose, scope the failure to that purpose.

8 · Working here

Run a type check and the test suite before you finish. The suite is around two hundred tests and passing; the two type errors in the sandbox workspace are pre-existing.

There are three Salesforce orgs — development, staging and production. Metadata changes are made in development and promoted through staging to production using DevOps Center, with GitHub as source control for the Salesforce metadata. So schema work follows a real pipeline: make the change in development, promote it, and do not hand-edit production.

Trail OS itself points at production. That is the asymmetry to hold in your head: the schema has a promotion path, but the application reads and writes the live org directly. There is no staging deployment of Trail OS pointed at the staging org today, so treat every write from the application as real. The connector also authenticates as a named personal account for now — moving it to a dedicated integration user is open work, and it will change the permissions your code runs under.

A practical consequence: when you add a field or object, it exists in development before it exists in production, so application code that depends on it will fail against production until the change is promoted. If something the schema says should be there is missing, check which org you are looking at before assuming it was never built.

Never add a Salesforce field or object without checking the org first — and be explicit about which org you checked. The documented model and the deployed model have diverged before, in both directions, and a field present in development and absent from production looks identical to a field that was never created.

Verify integration work against the org, not a mock. The most expensive bug in this codebase would have been caught by one real query.

9 · Where the documentation lives

Being reorganized, so this matters. Epics, features and cases are moving into Salesforce, with knowledge articles supporting Trail OS. The older strategy and requirements documents are being archived rather than maintained.

What that means for you in practice: do not treat an archived document as a specification. Several describe objects that were never created, integrations listed as planned that have shipped, and a version of the methodology that was wrong. They are useful for understanding intent and unsafe as instructions.

Four things are authoritative, in this order. The Salesforce org for anything about data. The code for anything about structure or behavior. Salesforce epics and features for what is planned. The design system for anything visual.

If you find this document wrong, it is wrong — fix it. A contributor pack that nobody trusts is worse than none, because it costs a day before it is discovered.
